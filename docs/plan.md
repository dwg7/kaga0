## 完了項目の詳細(2026-08-30、優先度1表からのリンク先)

### bvmapのz16再抽出(藤村さん指摘、2026-08-30)

「札幌で細かい建物が出てこない」という指摘から発覚。抽出時に`--maxzoom=14`
(VBM/VLCMに合わせただけで、bvmap自体の実際の最大ズームを未確認だった)と
していたが、GSI `optimal_bvmap-v1`原本のPMTilesヘッダを直接確認したところ
**実際はz16まで存在**(z4-16)。加えて`bvmap-dark.json`のスタイル定義を全レイヤー
精査したところ、`bvmap-道路縁`・`bvmap-構造物線`・`bvmap-軌道の中心線`等、
複数レイヤーが`minzoom=17`(=ネイティブデータ無しのオーバーズーム前提)で
設計されていることを確認——**藤村さんの「地理院スタイルはオーバーズームを
活用した複雑なズーム処理をしている」という見立ての通り**だった。z14打ち切りは
z15-16のネイティブデータそのものを欠落させ、z17でのオーバーズーム表示も
機能しなくしていた。

**対応**: 同じ北海道拡張bbox(稚内・択捉島まで)でz16まで再抽出(2.3GB、
z14版473MBから約5倍)。style.json(kitavolca/bvmap-only両方)の
`sources.bvmap.maxzoom`を14→16に修正。ディスクは12GB free時点での作業で
安全域(z14版と入れ替えで実質+1.8GB)。

**教訓**: PMTilesを`pmtiles extract`する際は、抽出元のズーム範囲を必ず
ヘッダで確認してから`--maxzoom`を決める(他データセットのズーム範囲を
流用しない)。VBM/VLCMの5-14はkitavolca側で確認済みの値だったので問題
なかったが、bvmapは確認を怠っていた。

**新たなtrade-off(実機反映後に判明)**: z16版デプロイ後、fpsが12-15程度に
低下(z14版・同じzoom_bias=2.0では29-33fpsだった)。建物等の詳細データが
増えた分、実際に描画するジオメトリ量が増えたためと考えられる——「精細さ」と
「fps」のtrade-offが再び表面化した形。次のアクション候補:
(a) 許容してこのまま使う、(b) zoom_biasを下げて相殺する、(c) 建物レイヤーの
描画コストを個別に見直す(fillのみでlineの外周描画も重ねているため、
外周線レイヤーを間引く選択肢もある)。要藤村さんの判断。

### マウスホイールでのズームイン/アウト(独自実装、2026-08-30)

Slintの`linuxkms`バックエンド(`calloop_backend/input.rs`)を再確認したところ、
`PointerEvent::Motion`/`MotionAbsolute`/`Button`のみ処理し、`Axis`(wheel/
scroll)は`_ => {}`で握りつぶされることを改めて確認。Slint内部に
`libinput_event_hook`という横取り機構は存在するが、`slint-cpp`(C++バインディング)
層には配線されておらず(`api/cpp/lib.rs`に該当コードなし)、C++からは利用不可
と判明。

実装前に「Yuisekiさんがtouchイベントをどう統合したか」を確認(藤村さんの
提案)——`main_gl.cpp:638`のコメントに明記の通り、**touch/mouseは両方とも
Slint標準のpointer-eventパイプラインで処理**(`MotionAbsolute`/`Button`に
自然にマップされるため、特別な回避策は不要)。evdev直読みが使われているのは
唯一「Slintが構造的に対応できないもの」(アイドル検知用の汎用アクティビティ
監視)のみ。ホイールもこの同じカテゴリに該当するため、直読みは設計として
一貫性がある、と確認した上で実装。

**実装内容**: `main_gl.cpp`に`REL_WHEEL`能力を持つデバイスを自動検出する
生evdev読み取りスレッドを追加(`MAPLIBRE_WHEEL_DEVS`で上書き可能、
キーボード自動検出と同じ`EVIOCGBIT`パターン)。スレッド安全性は既存の
`net_ssid`ポーリングと同じ設計——**バックグラウンドスレッドはatomicな
カウンタに加算するだけ**で、Slint/mbglには一切触れない。UIスレッド上で
200ms周期実行中の`flyto_timer`(既存、他のバックグラウンド→UI受け渡しの
定位置)がカウンタを読み出し、`smap->handle_wheel_zoom()`を直接呼ぶ
(オンスクリーンのズームボタンが呼ぶのと全く同じ関数)。ズームの中心点は
画面中央固定(オンスクリーンボタンと同じ挙動)。

**実機で動作確認済み**(藤村さん確認: 「ホイール利いているよ!素晴らしい!!」)。
CLAUDE.md v0成功条件「ホイール=拡大縮小」達成——今夜の当初、Slint上流の
制約により実現不可と結論していたものを、独自実装で覆した形になる。

### ステータスバーの取捨選択(2026-08-30藤村さんの疑問から)

上部ステータスバー(Yuisekiさん設計、GPS/時計/Wi-Fi SSID/バッテリー)のうち:
- **GPS・バッテリー**: m329に該当ハードウェア無し→自動的に非表示(対応不要)
- **Wi-Fi SSID表示**: kagaの「オフライン運用」という核心方針と表示内容が矛盾する
  印象がある(SSIDが見えている=Wi-Fiに繋がっている、という状態を積極的に見せる
  意味があるか要検討)。隠す/残すは藤村さんの判断待ち
- **時計**: 会議・打合せでの実利用(CLAUDE.md成功条件5)には便利。残す方向で良さそう
- **fps・解像度の追加表示**(藤村さん要望): 開発・チューニング用途では有用。
  `main_gl.cpp`に既にfps計測ロジック(`perf_log_`)があるので、ステータスバーへの
  接続は比較的小さな変更
- **CPU/GPU使用率(%)・コア温度の表示**(藤村さん要望、2026-08-30):
  CPU使用率は`/proc/stat`の差分計算、温度は`vcgencmd measure_temp`または
  `/sys/class/thermal/thermal_zone0/temp`で取得可能(m329で動作確認済み、
  [docs/m329-hardware-specs.md](m329-hardware-specs.md)参照)。GPU(V3D)使用率は
  RPiで一般的な取得手段が無く(vcgencmdにGPU負荷率の項目が無い)要調査——
  代替として「フレームあたりのレンダリング時間」(`main_gl.cpp`の
  `MAPLIBRE_PERF`計測が近いものを持っている)で代用するのが現実的か
- 上記2点(fps/解像度、CPU/GPU/温度)は**本番appliance時は非表示、開発時のみ
  表示**という切り替え(環境変数一つで良い)が望ましいか要相談
- **難易度**: 小(CPU使用率・温度・fps/解像度)〜要調査(GPU使用率)〜要相談(Wi-Fi SSIDの扱い)

- **難易度**: 小(style.jsonのURL書き換えのみで試せる)
- **優先度**: 中(効果不明だが試すコストは低い)

### VBMのズームレベル割り当ての見直し(2026-08-30藤村さんの所感、着手保留)

実機で見比べた印象として、**bvmap(GSI「最適化ベクトルタイル」)はズームレベルごとの
情報量設計(どのズームで何を見せるか)の完成度が高い**一方、**VBM(火山基本図)は
ズームレベル割り当てが「急ぎすぎ」——本来もう少し高いズームで出すべき情報が、
より低いズームから出てしまっている印象**とのこと。

考えられる背景(未検証の仮説):
- bvmapはGSIが長期間かけて調整してきた全国スケールの汎用ベースマップ
- VBMは火山基本図としての元データ(紙地図由来?)を機械的にベクトルタイル化した
  可能性があり、Web地図の「ズームに応じた情報量の間引き」という発想が
  薄いまま変換された可能性がある
- 今回導入した`MAPLIBRE_ZOOM_BIAS`(効果あり、+2.0で採用中)は、まさにこの
  ギャップを**アプリ側で強引に補正している**とも言える(VBMが「早すぎる」なら、
  全体を底上げして帳尻を合わせている状態)

**今は着手しない**。ただし今後の選択肢として:
1. VBM側のスタイル定義(各レイヤーのminzoom/maxzoom、線幅/文字サイズの
   zoom-expression)をkitavolca側で見直す(本丸だが影響範囲が大きい)
2. kaga側のstyle.jsonで、VBMレイヤーだけに追加のzoom補正をかける
   (対症療法だが影響範囲は小さい)
3. 何もしない(`MAPLIBRE_ZOOM_BIAS`で十分事足りている、という判断もあり得る)
- **難易度**: 大(1の場合。kitavolca側の設計判断に踏み込むため)〜小(2の場合)
- **優先度**: 低(現状`ZOOM_BIAS`で実用上困っていない。認識の記録が目的)

### 解像度の段階的引き上げ

1920x1080(強制設定)を起点に、段階を追って解像度を上げつつfpsを計測する
(藤村さんの元々の関心事)。ズームバイアスと合わせて「見た目の情報密度」と
「fps」のバランスを探る。
- **現在のベースライン数値**(zoom_bias段階別、196レイヤー版、1920x1080):
  - bias 0: 約15.8fps
  - bias +1.0: 約24fps
  - bias +2.0: 約29-33fps(拡張bvmap込み)
- **次のステップ**: `cmdline.txt`の`video=HDMI-A-1:...`を変更し、
  2560x1440や4K(JAPANNEXTディスプレイのネイティブ解像度)でも同様に計測
- **難易度**: 小(設定変更+再起動+計測)
- **優先度**: 中(v0の「快適なパン・ズーム」を数値で裏付ける作業)

## 優先度3: チャレンジ目標(藤村さん命名、大きめの技術検討が要る)

### VBM地物へのマウスオーバー属性表示

画面左下(Dance/Calmボタンがあった位置)に、ポインタ直下の火山基本図地物の
属性(GeoJSON properties)を表示する。
- 必要な技術要素:
  - `mbgl::Map::queryRenderedFeatures`相当のC++ API呼び出し経路の確保
  - Slint側でのドラッグ無しhover検知(既存の`TouchArea.moved`はドラッグ処理と
    共用中のため、素のマウス移動をどう拾うか要調査。Slintの`TouchArea`が
    press無しのmove/hoverイベントをそもそも配送するのか自体から要確認)
  - 属性表示パネルのUI設計(固定パネル/追従ツールチップ等)
- **難易度**: 大(Slint側のhover検知が未知数。上流ドキュメント/ソース調査が要る)
- **優先度**: 低〜中(v0成功条件には無いが、会議・打合せでの説明用途には価値が高い)

### フォント・スプライトの完全オフライン化

`glyphs`(`https://gsi-cyberjapan.github.io/optimal_bvmap/glyphs/...`)と
`sprite`(同ドメインの`sprite/std`)が今もGitHub Pages依存。kitavolca由来の
既存事情(今回新規に持ち込んだものではない)だが、bvmapと同様に一度取得して
ローカルPMTiles的資産として持ち込めば解消できるはず。
- **影響**: v0成功条件には非該当(ラベルが出なくても地物の色・形は表示される)。
  ただし完全オフライン化という核心方針には抵触
- **難易度**: 中(glyphsはPBF形式で256文字範囲ごとのファイル群、スプライトは
  PNG+JSON。取得・ローカル配置自体は単純だが、量が多い)
- **優先度**: 低(v1「背景地図強化」で本格対応が妥当)
