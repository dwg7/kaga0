# 6. 実機のホスト名は個体固有のコードネームとし、"kaga0"はプロジェクト名として扱う

- ステータス: 承認(藤村さんの最終判断で変更可)
- 日付: 2026-08-29

## 状況

kaga0プロジェクト用の最初のRaspberry Pi 4実機には、シリアル由来の個体識別名と、
それに対応する専用SSH鍵ペアが本セッション以前からあらかじめ用意されていた。
同様に、動かしているソフトウェア(プロジェクト)とは独立した、個体ごとの
コードネームで機体・鍵を管理する慣習が既に存在すると判断できる
(具体的な個体名・鍵ファイル名は本リポジトリには書かず、`.env`にのみ置く — [0007](0007-secrets-policy.md)参照)。

一方、CLAUDE.mdの初期ドラフトではRaspberry Pi Imagerでのホスト名設定例として
機械的に `kaga0` を書いていたが、これはリポジトリ名(=プロジェクト名)をそのまま
転記しただけで、既存の個体命名慣習とは無関係に決めたものだった。

## 決定

- **物理ホストのネットワーク上のホスト名(mDNS等)は、個体固有のコードネームを使う。**
  実際の値は`.env`の`KAGA_HOST`にのみ記録し、リポジトリにはハードコードしない。
- **`kaga0` はプロジェクト・ソフトウェアの呼び名として使う**(リポジトリ名、
  systemdサービスの説明文、ドキュメント上の一般的な参照先など)。ホスト名としては使わない。
- ロードマップ上の将来のkaga1・kaga2等の実機も、それぞれの個体コードネームを
  ホスト名として使い、「どの個体が現在どのプロジェクトの役割を担っているか」の
  対応関係は、公開リポジトリではなく手元の`.env`や個人の管理台帳で追跡する。

## 結果

- 良い点: 個体(ハードウェア)とプロジェクト(ソフトウェア役割)の対応が将来変わっても
  (実機が使い回される、あるいはプロジェクトが複数実機にまたがる等)、ホスト名を
  変える必要がない
- 良い点: 既存の鍵管理慣習(個体ごとに専用鍵を用意する)とも自然に一致する
- トレードオフ: このリポジトリの読者は「kaga0」というホスト名で実機に
  アクセスできるとは限らない。ドキュメント・スクリプトでは実機を指すのに
  常に `$KAGA_HOST`(`.env`で設定)を使い、特定の個体名をリポジトリにハードコードしない
